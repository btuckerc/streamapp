# Implementation and research decisions

## Desktop background fill

The [OBS aspect-ratio guide](https://obsproject.com/kb/aspect-ratio-guide) recommends filling unused canvas space rather than stretching a source (distortion) or enlarging it (content loss). StreamApp preserves the sharp aspect-fit desktop/window and composites a configurable background behind it. Settings → Layout owns this section; the quick menu has no new controls. Existing settings retain Black.

- **Color:** opaque custom sRGB, quiet and inexpensive.
- **Image:** aspect-fill imported artwork behind the sharp source; transparency uses the selected fallback color. Images are oriented/downsampled to 2048 pixels and copied as PNGs into app-owned storage, so moving the original does not break a setup.
- **Blurred desktop:** a separate enlarged copy, quarter-resolution Gaussian blur, clamped before filtering and cropped afterward. Only the background is blurred. This is the recommended subtle fill; it can still reveal broad shapes/colors from the already-captured source.
- **Mirrored wallpaper:** takes one wallpaper-only screenshot from the selected display's rendered WallpaperAgent surface using [ScreenCaptureKit](https://developer.apple.com/documentation/screencapturekit/scscreenshotmanager/captureimage(contentfilter:configuration:completionhandler:)). `NSWorkspace.desktopImageURL(for:)` returned the default beach image on this Mac, not its active mountain wallpaper, so file URLs and downloaded-asset guesses are not used. Window capture chooses the display containing the largest portion of the window; the snapshot is cropped to the window or Dock-fit region. Captured app content is never used for this mode. Identification requires one on-screen, negative-layer `com.apple.wallpaper.agent` window matching the display bounds. That window identity is an OS implementation detail, not a guaranteed wallpaper API; missing or ambiguous matches use the solid fallback.

Snapshots refresh on source changes, Space/display/wake notifications and wallpaper-store filesystem events (without parsing private settings). Unrelated settings retain the snapshot. The reflected background is baked once per wallpaper/geometry/color change, rather than reevaluating reflection filters every video frame. Animated wallpapers remain still snapshots between refresh events; continuous animation synchronization would require ongoing capture.

The Metal preview uses transaction-synchronized presentation so its drawable updates participate in the surrounding native UI composition. Following Apple's [`presentsWithTransaction`](https://developer.apple.com/documentation/quartzcore/cametallayer/presentswithtransaction) contract, it commits the command buffer, waits until scheduled, then calls `drawable.present()` rather than scheduling presentation on the command buffer. This addresses a possible compositing cause of corrupted native controls; the original corruption's root cause has not been isolated.

Implementation uses [Core Image's Gaussian blur, affine tiling and compositing filters](https://developer.apple.com/library/archive/documentation/GraphicsImaging/Reference/CoreImageFilterReference/index.html). The reflected tile uses an explicit identity transform: the runtime CIAffineTile default scales by 0.4, which is not acceptable for edge continuity. Native pixel regression covers nonzero image/canvas origins and repeated reflection across wide bars. Static image loading and immediate thumbnail decoding run outside the compositor queue; changed paths clear stale images and stale completions cannot replace newer choices. The same FrameRenderer path feeds preview and encoded output. Camera/chat layering and Dock geometry remain unchanged.

## Product surface

StreamApp is an AppKit `NSStatusItem` + `NSPopover` hosting SwiftUI cards and a separate settings window. The presets are **Desktop** and **Full Camera**, with independent chat rendering, chat side/width, webcam corner/size, device selection and live audio controls. Existing scene identifiers remain unchanged in saved settings; missing configuration fields decode with defaults rather than discarding older settings.

The Usage Bar reference was `../usage-bar/Sources/CodexBar/`: `UsageMenuCardLayout.swift` supplies the compact 20pt horizontal-padding/section rhythm; `StatusItemController+MenuPresentation.swift` illustrates native SwiftUI hosting and measured layouts; `StatusItemController+MenuTracking.swift` documents why frequent meter updates should not rebuild a synchronously tracking NSMenu. StreamApp uses a popover and one stable status item. Meters sample at 5 Hz; output health samples at 1 Hz. Preview presentation runs independently of SwiftUI updates.

Popover placement is owned by AppKit: one retained hosting controller is sized and laid out before `show(relativeTo:of:preferredEdge:)`. There is no `popoverDidShow` frame correction; that previous correction visibly moved the already-open window. Animation is disabled for immediate menu-like presentation (Apple documents `animates` as a hint, not a guarantee). Dictation's `src-tauri/src/lib.rs` attaches its Tauri menu with `show_menu_on_left_click(true)`; Usage Bar's `StatusItemController.swift` attaches `NSMenu` to the status item. Neither is evidence for manually moving an already-shown popover. StreamApp retains NSPopover for live sliders/meters, using [AppKit anchoring](https://developer.apple.com/documentation/appkit/nspopover/show(relativeto:of:preferrededge:)) and [animation policy](https://developer.apple.com/documentation/appkit/nspopover/animates).

Source/device/output settings lock during a session. Scene selection, chat geometry, webcam enable/position, gains and mutes remain live. Start does not silently grant permissions or substitute a synthetic input for a missing real source. Broadcasting requires explicit confirmation; stop stays visible outside scrolling controls.

The pinned menu output controls use one **Record / Stream / Both** selector, also available in Outputs settings, and a single **Start / Stop** button. The selector maps atomically to recording/streaming flags; saved server/key/test settings do not choose the mode. Record never reads the key or validates/uses the server and ignores a retained bandwidth-test setting. Selecting Stream/Both or pressing Start with invalid streaming configuration opens a focused connection setup using the existing RTMP/RTMPS validation and Keychain storage. Completing setup does not start output or mark general onboarding complete. Broadcast confirmation still precedes streaming. Idle mode captions are omitted; the non-live bandwidth-test indicator remains. Mode selection is unavailable during a session. Legacy settings with both outputs disabled normalize to local recording.

Missing capture authorization is a setup state: a single **Finish permissions setup…** action above the popover meters and at the top of Settings lists missing screen/system-audio, camera and microphone access. It opens the existing onboarding Connect step regardless of `onboardingCompleted`; settings/menu per-source permission buttons are removed. Granted access disappears from the list, and the entire prompt disappears when complete. Synthetic demos do not require permissions. Idle preview preflights only its configured inputs and waits without opening devices when permission is missing, rather than producing repeated authorization errors. Other capture/output failures remain visible; explicit recording preflights still enforce authorization. No permissions are requested automatically, and an active session must stop before opening setup.

The application-defined popover closes on outside clicks and Escape. Status-item clicks are excluded from local/global dismissal monitors so the button's action toggles once rather than closing on mouse-down and reopening on mouse-up.

**Fit 16:9** restores the original `CFPreferences` write plus a targeted `SIGTERM` to the running `com.apple.dock` process. Size and temporary visibility are committed together before that restart, rather than showing a small Dock and resizing it in a second transition. This replaces the System Events implementation; no Automation entitlement or private CoreDock API is used. Handoff, recents, pinned items, animation and delay preferences are untouched. Apple’s [Dock management schema](https://github.com/apple/device-management/blob/release/mdm/profiles/com.apple.dock.yaml) specifies tile sizes 16…128.

The target comes from `SceneGeometry.desktop`: display height minus display width divided by the desktop slot's aspect ratio. Chat therefore requests a smaller Dock. An impossible target saturates at the smallest Dock. Bounded feedback uses pixel-size preferences; a one-second active-fit monitor follows changes to reserved height, Dock contents, displays and chat geometry. Size corrections restart Dock, while a saturated size is accepted without repeated restarts. Capture uses the measured region above Dock, preserving the menu bar and desktop width; the existing compositor aspect-fits that region into the scene. A positive reservation and an on-screen Dock surface on the selected display are required before publishing a crop.

Region changes publish through StudioModel and call `SCStream.updateConfiguration` on an already-running menu preview without restarting its camera or audio. Original, pending and applied sizes are journaled privately. Restore checks ownership and preserves external size changes, including recovery of interrupted normalized-control journals from the previous implementation. [Apple documents Handoff icons](https://support.apple.com/en-us/102426), including Notes, as transient Dock entries from nearby devices.

Fit journals original auto-hide and the pre-fit bottom reservation. Disable restores exact saved pixels and original hiding in one preference transaction/restart; a newer manually hidden state is never made visible on exit. A hidden Dock must return to its pre-fit bottom boundary (within one point) before the journal is removed. A persisted recovery phase prevents the active-fit monitor from enlarging Dock again after an interrupted or timed-out restore. A failed enable rolls back through the same path. Legacy size-only journals leave visibility untouched. StreamApp does not move other apps’ windows; [Apple’s visibleFrame API](https://developer.apple.com/documentation/appkit/nsscreen/visibleframe) reports usable geometry, not a guarantee that existing windows reposition.

Twitch bandwidth tests use the documented `bandwidthtest=true` query only on recognized Twitch ingest hosts. Both test and live starts require confirmation. Twitch Inspector, not local FFmpeg progress, establishes remote delivery quality.

Dictation's `../dictation/docs/onboarding.md` supplied the Connect → Prepare → Try it structure, explicit permission recovery and optional real trial. StreamApp's trial copies settings and forces local recording with streaming disabled; live trial changes preserve that isolation. One task owns stop/finalization, including close during device startup. Onboarding completion is separate from the existing Codable settings schema.

Twitch uses the registered public client **StreamApp by btuckerc** with [Device Code OAuth](https://dev.twitch.tv/docs/authentication/getting-tokens-oauth/) and exactly `user:read:chat channel:read:stream_key`. No client secret or central backend is shipped. `TwitchSession` stores tokens atomically in Keychain, validates at startup and hourly, serializes single-use refresh rotation, and prevents cancelled requests from resurrecting an account. Twitch stream keys are fetched for the authenticated account immediately before confirmed output startup; local recording bypasses that request. Missing service choices default to Twitch; explicit Custom RTMP choices, stored keys and URLs are retained. Changing service clears stale validation feedback in both Settings and onboarding.

## Media path

```text
ScreenCaptureKit ─── latest-frame slot ─┐
AVCapture camera ─── latest-frame slot ─┼─ Metal/CoreImage composition
Cached local WKWebView chat snapshot ──┘          │
                                      VT encoder pixel-buffer pool
                                                 │
                                      hardware H.264, no B-frames
                                                 │
                                      libavformat timestamped FLV
                                                 │
Microphone + SCK audio → bounded native PCM mix → FFmpeg
                                                 ├─ Matroska recording
                                                 └─ bounded FIFO RTMP/RTMPS, reconnect
```

- `CaptureEngine.swift` owns main-actor lifecycle, authorization preflights and explicit device ownership. Capture callbacks use separate queues and replace bounded latest-frame slots, not an accumulating queue of frame tasks.
- `FrameRenderer.swift` composes on its own serial queue. Immutable pooled frames are reused when inputs/configuration have not changed; the 30 Hz encoder clock continues. Full raw video never crosses a process pipe. `GPUPreview.swift` retains only the latest composed IOSurface for program preview, or the captured camera buffer for an opt-in webcam view. Metal/CoreImage scales it into the drawable without CPU readback or repeating scene composition. One GPU submission is allowed in flight; rendering never waits for the preview. Hidden/occluded/offscreen views pause and release the mailbox. Diagnostic PNG export is an explicit one-off, not a presentation path.
- `SceneTransition.swift` interpolates scene changes over 350 ms with smoothstep easing. Camera-only geometry changes use 600 ms cubic-bezier(0.22, 0, 0.18, 1): a soft departure and gentle settle without overshoot. The time coordinate is inverted with bounded Newton iterations; settled frames bypass easing. Interruptions retarget from visible geometry, not a previous endpoint; completion settles to exact targets. Reduce Motion cuts. Full Camera retains sharp full-frame camera video; only the right chat panel plus a 48px kernel halo is cropped, downsampled to ¼ resolution, Gaussian-blurred on Metal and tinted. Text is composited afterward. There is no second encoder, full-frame blur or CPU blur path.
- The desktop webcam has rounded alpha clipping and a quiet black shadow, replacing the solid rectangular border. Core Image generates the rounded mask and blurs only its alpha silhouette; the camera remains sharp. Filter graphs are retained until geometry changes; no CPU mask rasterization or camera readback is introduced. Radius and shadow fade with the existing scene morph; settled Full Camera bypasses both. This follows [Apple's depth/material guidance](https://developer.apple.com/design/human-interface-guidelines/materials), but is encoded-frame styling, not actual AppKit Liquid Glass or refraction.
- Desktop webcam punch-in is a transient configuration flag excluded from Codable. The separately persisted `cameraPunchInSize` controls the existing 16:9 overlay, defaults to 52% of the desktop region's width and is bounded to 40–90%; normal size remains independently bounded to 12–40%. Missing saved values adopt 52%. Both menu and Layout settings edit the same preference, with the standard independent reset in Settings. Geometry preserves its 24 px corner margins and leaves desktop/chat unchanged; disabling the camera or leaving Desktop clears emphasis without discarding either saved size. `StudioShortcuts` centrally routes Carbon hot-key IDs for annotation (⌃⌥⌘D) and punch-in (⌃⌥⌘V), with held-key deduplication and separate registration failures. Tablet Companion suggests Annotate / Webcam punch-in / Stroke width / Clear and stores V as a driver keystroke; no tablet-specific listener, extra capture session or background animation loop is added.
- Design research distinguished [OBS source scaling from cropping](https://obsproject.com/kb/sources-guide), [Ecamm camera overlays](https://support.ecamm.com/en/articles/3323618-using-overlays), and [Apple's Small/Large Presenter Overlay emphasis states](https://support.apple.com/guide/mac-help/use-video-conferencing-features-on-your-mac-mchlff01c919/mac). None specifies a universal ideal size. The initial 1.5× / 33%-width choice was rejected by the user as too timid; 52% and the longer curve implement that feedback while keeping most desktop content visible.
- `VideoEncoder.swift` requires hardware VideoToolbox H.264, three in-flight submissions and a six-buffer allocation threshold. `EncodedMuxer` preserves PTS/DTS and writes only compressed packets, with finite backpressure deadlines.
- `AudioMixer.swift` uses fixed-capacity stereo rings aligned to the host clock. AVAudioConverter handles interleaved/noninterleaved input and sample-rate conversion; a 100 ms playout allowance accommodates capture delivery. Gains/mutes are applied before mixing, absent/disabled sources are silent, late audio is discarded rather than replayed, and mixed peaks are bounded. There is no speaker-monitoring path.
- Microphone compression uses stereo-linked detection, a −18 dBFS threshold, 3:1 ratio, 6 dB soft knee, 10 ms attack and 150 ms release; no makeup gain or AGC. Nonlinear gain calculations run at 1 kHz, with sample-smoothed gain. A linked instant-attack/releasing final limiter caps PCM sample peaks near −1 dBFS without extra latency. This is not an oversampled true-peak limiter; AAC reconstruction may exceed the PCM ceiling.
- Channel meters observe post-gain/mute/processing sample peaks; the output meter observes the final protected mix. Peaks accumulate until one atomic UI read, so short transients survive 5 Hz polling. The UI maps −60…0 dBFS logarithmically and labels silence; gain reduction is reported separately. Speaker playback volume, integrated LUFS and dBFS are different quantities.
- Visible-menu audio checks reuse the mixer with a bounded 20 ms pull clock. Video defaults Off. Layout runs the existing compositor without an encoder at 30 Hz with a four-buffer allocation ceiling; Webcam uses the latest camera frame directly. A generation-guarded serialized transition releases preview resources before recording and on menu close. No recording or broadcast starts; configured chat may connect when Layout is enabled. Gain/mute changes reconfigure the mixer without restarting devices. Off cancels queued camera startup before teardown.
- `MediaOutput.swift` uses private 0700 temporary directories and 0600 named FIFOs, avoiding fragile inherited-FD assumptions or global `dup2` changes in the GUI process. PCM writes preserve partial-write boundaries and fail on a stalled consumer rather than silently dropping bytes. FFmpeg stream-copies H.264 and encodes only AAC. RTMP can reconnect independently of the local recording.
- FFmpeg emits machine-readable progress once per second through a private pipe. Recording confidence uses advancing output timestamps/frame counts and actual file size, not process launch or preview activity. No progress for three seconds after output begins is reported as stalled; startup gets ten seconds. Broadcast-only progress never claims remote delivery. Readers remain open through output finalization.
- Stop releases capture, drains VideoToolbox, closes media transport, and waits for FFmpeg to finalize. Failure states are surfaced, not silently downgraded to a fake or software path.

## Chat, settings and privacy

`TwitchChatFeed` uses per-user [EventSub WebSockets](https://dev.twitch.tv/docs/eventsub/handling-websocket-events/) and the selected broadcaster's channel, independently of output identity. It subscribes to messages, message deletion, user-message clearing and full chat clearing. It deduplicates a bounded 2048 event IDs, enforces keepalive deadlines, drains the old connection during reconnect handoff, retries transport failures with bounded backoff, and clears potentially stale text after gaps. Revocations stop reception. There is no posting API or write scope.

`Chat.swift` loads bundled HTML and serially batches structured events into an owned renderer. It never loads remote HTML. Native pending events are bounded to 256 and the DOM/data model to 100 messages; the color cache is capped at 256. Text uses DOM text nodes, with usernames restricted to hex RGB colors. Official EventSub emote fragments take precedence over case-sensitive, whitespace-delimited catalog codes; channel entries precede globals, with Twitch → 7TV → FFZ → BTTV precedence within each scope. Shared-chat messages from another channel use globals rather than the selected channel's catalog. Missing images and malformed fragments retain plain text. Shared-chat source labels and moderation events are preserved.

`ChatEmoteCatalog` loads public global and channel catalogs from Twitch Helix, 7TV v3, BTTV v3 and FFZ v1. Provider requests run concurrently and identical in-flight requests coalesce. The actor retains at most 36 provider/scope entries with a 30-minute TTL; failures retain stale data for five minutes. Active emote-enabled chat refreshes every 30 minutes, not per message. Third-party responses are capped at 8 MiB during transfer, with no redirects, bounded timeouts and at most 8192 codes per provider/scope. Twitch uses the existing read-only authenticated session; third-party requests send no Twitch credentials.

Catalog URLs and the image CSP allow only HTTPS Twitch, 7TV, BTTV and FFZ CDNs. Rendering uses Twitch's static format, 7TV's `static_name`, BTTV's `.png` variant (the `.webp` route can animate), and FFZ's static `urls`. Images load lazily with asynchronous decoding, preserve bounded aspect ratios, and may form adjacent zero-width stacks. FFZ static flip/grow/color modifiers are supported; animation flags are ignored. FFZ `public`/`hidden` govern adding emotes and picker visibility, not rendering an active set. Private/personal packs, provider update sockets, remote fonts, bot HTML and animated effects are intentionally excluded.

Snapshotting is invalidation-driven, one request in flight and at most 30 Hz. A coalesced one-shot timer runs only when dirty; clean chat has no polling timer. Identical connection statuses do not mutate the DOM. Retina backing scale is measured so snapshots match the requested output width ×1080 pixels. DOM/font/resize/image-load invalidations cover this text/static-image renderer; this is not a general-purpose browser source.

`ChatAppearance` persists individual options with per-field decoding defaults. Presets (Terminal 24 px, Compact 20 px, Large text 32 px, Monochrome 24 px) are value bundles, not a second persisted source of truth; unmatched options display Custom. All use monospace `<username> message`, 1.5 line height and bottom-aligned newest messages. The size control spans 20–48 output pixels. The default background is solid `#10151c`; optional translucency is fixed at 90%. Exact Twitch RGB is retained when it reaches 4.5:1, otherwise blended toward white. Contrast calculations for translucency assume white behind the panel, the worst case. Body, metadata and highlight colors meet the same target. This follows [WCAG contrast guidance](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum), not full WCAG compliance for raster video; Twitch's [chat documentation](https://dev.twitch.tv/docs/chat/) prescribes no overlay type size. Downscaled playback reduces effective text size.

Appearance edits update the existing preview/output Chat instance instead of restarting EventSub. Test chat uses the configured panel width and offers a selectable native text transcript with manual scrolling; only that test view requests transcript serialization. Moderation clears both the render data and transcript, including after preset changes. Legacy anglbot commands (`!help`, `!fish`, permissions, cooldowns and custom commands) remain bot-owned; the app exposes a concise command reference rather than inactive execution controls. No bot process is started.

Chat stays alive across layout switches when enabled. Disabling Render chat stops and releases WebKit/EventSub, clears its image and skips panel/blur composition; the desktop expands to full width. The macOS WKWebView backing must have `drawsBackground=false` as well as transparent CSS/under-page color. Camera-off clears the image immediately; leaving Desktop preserves only its last screen frame for the short exit morph, and returning restarts real screen capture.

Launching the app does not capture or enumerate private windows. Source listing and permission requests are explicit UI actions. Settings contain neither OAuth tokens nor stream keys. OAuth credentials and manually saved custom keys use Keychain; automatically retrieved Twitch keys stay in memory. Raw FFmpeg stderr is never displayed or persisted because it can echo an RTMP key. This is a local non-sandboxed app: privileged local inspection is outside this protection boundary.

### Physical-notch teleprompter

`TeleprompterOverlay` owns two stable nonactivating AppKit panels: an animated text body and a stationary chevron immediately left of the physical camera cutout. One `NotchSilhouette` draws concave 8-point top shoulders and convex lower corners on both surfaces. The opaque sRGB-black handle backing bridges the left safe-area edge and ends underneath the camera midpoint: it cannot leave a seam or square off the hardware notch's native right corner. Shoulder space is added outside the text/button layout, preserving text width and the chevron's position. The handle never shares the body's resizing animation. The body attaches to the screen's top edge, retracts on any click, and preserves the current mode/page. Reduce Motion cuts immediately; a generation check prevents an old collapse completion from hiding a newer expansion. Off orders out both panels. A notched display is preferred, otherwise the selected/main display is used.

`TeleprompterModel` bounds UTF-8 Markdown imports to 1 MiB and regular files, strips comments, renders inline emphasis and cue headings/lists, and splits `---` cues into measured three-line attributed-text pages. TextKit character ranges preserve all rendered characters across soft wraps, including long tokens and multilingual text. Reload replaces old content and resets paging; failures clear stale text. Template creation and import use native save/open panels. Only text appears in the notch; mode, file, privacy and page controls live exclusively in Settings → Prompter, not the quick menu.

Twitch mode reuses the read-only `TwitchChatFeed` and selected channel, independent of program chat rendering, retaining at most six messages and applying deletion/user-clear/full-clear events. Mode/source generations reject late events. `StudioShortcuts` registers unmodified Left/Right only for an expanded nonempty transcript, releasing them while editing active StreamApp settings, choosing files or showing a modal dialog. Paging clamps at either end.

Both window IDs are explicit private entries in the shared recording/preview capture policy. **Show StreamApp windows** does not include either one; `teleprompterInCapture` is a separate persisted opt-in with a false migration default. ScreenCaptureKit always excludes our process, then excepts known ordinary windows when requested, annotation ink, and the teleprompter only when opted in. Unknown windows fail closed. Direct capture of a private teleprompter window is rejected. Filter changes are serialized and generation-guarded; the overlay is hidden during a privacy transition and shown only after the new filter applies. No reliance on `NSWindow.sharingType` privacy behavior, compositor overlay, extra encoder or protection from third-party capture is claimed.

### Native annotations and exclusions

`AnnotationOverlay.swift` uses a transparent floating AppKit canvas and a separate toolbar. Retained pressure-width paths update only dirty regions; storage is bounded to 512 strokes / 100,000 committed tessellation samples, plus at most 32 tail samples per stroke. Pen, highlighter, eraser, freehand arrows, straight lines/arrows, ellipses, rectangles, undo and clear require no WebKit, polling loop or third-party drawing SDK. **Control–Option–Command–D** toggles drawing; Escape releases pointer input while preserving ink. The extra Control modifier avoids macOS's Option–Command–D Dock shortcut. Annotations apply to Desktop display capture, not single-window capture or Full Camera.

Drawing uses AppKit's plus crosshair through canvas cursor rectangles; leaving drawing restores the normal cursor. The menu's **Clear annotations** calls the same canvas clear operation as the private toolbar and works after Escape.

**Settings → Drawing** stores smoothing, width, stroke/highlighter RGB and fill RGBA independently in UserDefaults, without changing the broadcast settings schema. The original RGB keys remain the stroke color; highlighter defaults yellow and fill defaults transparent. Every stroke snapshots its style. Ellipse/rectangle fills reuse their centerline geometry, render beneath the outline, and participate in object erase; transparent fills allocate no fill path. The quick palette exposes Stroke, Fill, and Highlighter targets. Freehand input uses real tablet pressure, lightweight streamlining and midpoint quadratic interpolation of position/radius; only the unfinished tail is rebuilt. Highlighter coverage uses a single 30%-opacity fill per stroke, avoiding alpha buildup at segment joins. No OCR, text detection, additional screen capture, or background analysis is involved.

**Eraser** defaults to Object; Partial preserves the clear-blend brush. The mode is persisted and snapshotted at contact. Object erasing intersects a swept tip footprint with candidate filled geometry after a bounding-box rejection, including arrowheads and excluding areas already removed by later partial erasers. Hollow shape interiors are not targets. Affected objects are hidden immediately and retained by one undo record per gesture; empty erasures add no history. Undo restores the original objects in place, preserving paint order and partial masks. Geometry remains under the existing storage caps; at most one additional object-erasure record per retained drawable object is possible. Erasing is allowed at the drawing limit, but Clear is still required to reclaim retained undo geometry.

Arrow defaults to freehand ink with a width/length-capped head following its terminal direction. **Straight** switches Pen/Arrow to drag endpoints; Shift snaps these to 15° angles and constrains ellipse/rectangle to circle/square. Canvas-local mouse button events use persisted action mappings (secondary → tools, middle → Straight by default). Raw tablet masks do not identify physical side buttons reliably after driver mapping and are not used for actions. Down/up tracking deduplicates holds. The eight-sector radial picker, color palette, and width picker sit above the canvas and are excluded from capture with the other application UI. `stopDrawing()` dismisses pickers and clears held input.

Freehand arrow heading uses a single anchor trailing the tip by up to 6 pt. This spatial smoothing prevents tiny release reversals from flipping the head, remains independent of event rate and the ink-smoothing setting, and still follows deliberate turns. The tip stays at the actual endpoint; straight-arrow geometry is unchanged. Cost is constant per event with no history buffer.

The mapped Tools button starts a one-shot 250 ms hold timer. A quick release toggles Pen/Erase (other tools return to Pen). Holding shows eight radial sectors, clockwise from north: Colors, Pen, Arrow, Rectangle, Ellipse, Erase, Undo, Highlight. Movement updates only the highlighted sector; release commits it. The center cancels. Colors opens a separate clickable radial palette with Stroke/Highlighter/Fill targets, No fill, and Back to tools; selecting a color does not switch tools. The held-tool panel ignores mouse input so the canvas retains the button sequence; a temporary local monitor consumes tip clicks and forwards side-button releases. Escape, deactivation, drawing exit, or another picker cancels the gesture and removes its timer/monitor. No idle polling is used.

**Hold to straighten** is a separate persisted drawing preference, on by default. The default width is 6 pt; existing saved values are retained. With hold mode enabled, the mapped Straighten button temporarily enables Straight and can convert the active Pen/Arrow gesture to endpoint geometry. Release clears temporary mode without altering the current stroke; the next stroke uses the independent toolbar mode. Escape/Done clears pending holds. Straight Pen/Arrow and arrowheads use the freehand pressure-to-width mapping, retaining last contact pressure on pen-up. Ellipse/rectangle outlines remain uniform at configured width.

The algorithm draws on the distinction between streamlining and outline smoothing in [perfect-freehand](https://github.com/steveruizok/perfect-freehand) and [tldraw's draw documentation](https://tldraw.dev/sdk-features/draw-shape). The arrowhead design follows the proportional sizing principle in [tldraw's arrowheads](https://github.com/tldraw/tldraw/blob/main/packages/tldraw/src/lib/shapes/arrow/arrowheads.ts). This is an independent native implementation, not a bundled tldraw SDK or a full editable-canvas replacement.

ScreenCaptureKit's [application filter with window exceptions](https://developer.apple.com/documentation/screencapturekit/sccontentfilter/init(display:excludingapplications:exceptingwindows:)) excludes StreamApp by default and selected apps, then explicitly includes the canvas. **Settings → Sources → Show StreamApp windows** persists an opt-in to include the app's menu, settings, and drawing toolbar in display capture. Changing it updates the active capture filter for both recording and streaming, or refreshes idle preview. The canvas is only added as an exception when its owning app is excluded, so ink remains included in either mode. Individual windows in otherwise included apps are excluded via the same exception list. Refresh/restart after excluded apps reopen. App bundle rules persist; window IDs do not survive StreamApp relaunch. This is an app capture policy, not protection from other capture software or a system-wide confidentiality boundary.

### Drawing-engine decision — 2026-09-20

**Retain the working native overlay in this installed build; choose tldraw rather than expanding the custom implementation into a full editable-canvas engine.** tldraw wins the documented feature comparison, not a measured latency or subjective-user-preference contest. A production replacement requires a valid license and a verified native host; neither is implied by a successful browser demo.

| Evidence | Current native overlay | tldraw |
|---|---|---|
| Drawing | Configurable pressure-aware smoothing, color/width, freehand/straight arrows and basic shapes | [Documented smoothing/interpolation, real pen pressure and simulated mouse pressure](https://tldraw.dev/sdk-features/draw-shape) |
| Editing | Fixed ink, undo and clear; no redo/selection | [Selection, shape manipulation and history APIs](https://tldraw.dev/docs/editor); parent exercised drawing, selecting/moving and erasing in the official custom-UI demo |
| Eraser | Object erase by default; optional Partial clear-blend brush; gesture-level undo | The exercised default eraser removed a whole stroke; splitting/editable-shape behavior is not claimed for the native engine |
| Accessibility | Native toolbar buttons; no semantic navigation among strokes | [Documented shape announcements and keyboard navigation](https://tldraw.dev/sdk-features/accessibility); VoiceOver inside WKWebView remains untested |
| Public ink/private UI | Real recording verified the two-window capture boundary | [Custom UI is supported](https://tldraw.dev/examples/custom-ui), but `hideUi` alone does not remove the context menu; requires deliberate native-toolbar and transparent-host integration |

The browser exercise used `https://examples.tldraw.com/custom-ui/full` in an isolated managed browser, with synthetic strokes only; it was not a WKWebView or tablet test. The reviewed release reference is [v5.4.2](https://github.com/tldraw/tldraw/releases/tag/v5.4.2). tldraw is a React drawing SDK, not a Wacom driver: native window ownership, global shortcut, click-through, display coordinates and ScreenCaptureKit inclusion still belong to StreamApp. [Installation docs](https://tldraw.dev/installation) support bundled/self-hosted assets; the default CDN must not become a hidden offline dependency.

[Current licensing](https://tldraw.dev/community/license) requires a production key. The [free hobby license](https://tldraw.dev/get-a-license/hobby) is discretionary and retains the watermark, even for personal noncommercial use. [Pricing](https://tldraw.dev/pricing) is annual, value-based and quote-only; no public dollar price is listed. Watermark-free use needs a commercial/custom arrangement. The current [LicenseManager source](https://github.com/tldraw/tldraw/blob/main/packages/editor/src/lib/license/LicenseManager.ts) contains native-protocol license support, but that does not establish the terms or price for a bundled WKWebView application. Ask the vendor for the appropriate native license.

Offline key validation is not a guarantee of zero network activity: current source and [issue #10034](https://github.com/tldraw/tldraw/issues/10034) conflict with older documentation about telemetry for watermark-bearing production/hobby keys. Verify the exact SDK version and license before promising offline behavior. No license was requested, terms accepted, or tldraw code bundled. Migration still requires transparent WKWebView/capture verification, private controls, and hardware input qualification.

### Wacom configuration research

The separate `~/src/wacom` Tablet Companion discovers global ExpressKeys and supported pen-button settings from Wacom's typed XML. Direct AppleEvents to `com.wacom.wacomtablet` provide tablet identity, connection state, and preference flushing. Suggested actions fill available keys in order (Annotate, Color, Stroke width, Clear); additional keys retain their current assignments. No fixed key or pen-button count is required.

Apply/Restore stages the driver's native restore file and invokes Wacom Tablet Utility `--restart`, then flushes and verifies readback. Per-control journals preserve the original assignments across repeated applies, migrate the old single-key restore point, and reject conflicting external changes. Optional pen setup maps discovered side buttons to native clicks and disables Press-and-Tap for hover activation; a separate restore point retains original assignments and mode. Tip/eraser settings and app profiles are untouched. This is version-sensitive integration: only recognized, uniquely matched settings are writable, not a universal vendor API. Physical event delivery remains a separate hardware check.

The [official macOS Device Kit](https://github.com/Wacom-Developer/wacom-device-kit-macos-api) documents AppleEvent operations. The [direct 6.4.14-1 installer](https://cdn.wacom.com/u/productsupport/drivers/mac/professional/WacomTablet_6.4.14-1.dmg) is obtainable without Center or an account. Its signed/notarized package has one mandatory payload, not a driver-only installation choice; it includes Center and background driver helpers. StreamApp itself includes no Wacom dependency, driver writes, or remapping service.

### Audio research boundary

[EBU R 128 s2](https://tech.ebu.ch/docs/r/r128s2.pdf) distinguishes playback environments and permits different streaming distribution loudness, including −20…−16 LUFS in its described adaptation case. It does not establish one universally enjoyable compressor preset or equate peak meters with loudness. The shipped preset is a conservative engineering choice, not a claim of LUFS normalization. Aggressive gating, automatic makeup/AGC, denoising and ducking are deliberately not added without evidence they improve this microphone/use case.

### Ableton / OBS audio qualification

**Decision:** retain native ScreenCaptureKit + AVFoundation + the existing timestamped PCM mixer. No virtual driver is required for ordinary Ableton stereo capture. Keep the performer’s monitoring in Live/the interface, not in StreamApp. Prefer one wired interface/headphones for playing; AirPods are a convenience listening path, not a low-latency reference.

**Observed local configuration:** Ableton Live 12.4.3 and OBS 31.0.1 are installed. Before this change, StreamApp's saved audio enabled both system audio and the default microphone, at unity gain, with mic compression enabled. OBS's saved `Untitled` collection has an `ABLETON_SCENE` using the `ABLETON` ScreenCaptureKit video source targeted at `com.ableton.live`; the saved current `Dev Time` scene uses a different screen source. Its global mic points at `BuiltInHeadphoneInputDevice`, which must be checked for availability. Explicitly configured OBS profiles inspected use 48 kHz stereo; the testing profile has no explicit Audio section. These are saved-file observations, not proof of current device routing. OBS/Live settings, audio hardware settings, permissions and stream credentials were not changed.

**Capture change:** visual SCStreams have audio disabled. A separate 48 kHz stereo audio stream uses a display-backed application filter independent of visual window/display selection and exclusions. Its 2×2/1 fps screen output is discarded, following OBS's screen-backed audio pattern; no additional compositor/encoder is created. A nonempty bundle ID includes only the current matching applications, while empty explicitly selects all other apps. Missing apps reject startup; termination of a selected process stops/finalizes the session rather than silently falling back or reacquiring another process. Normal scene/video-source changes leave the audio stream running. Preview uses the same policy. Application attribution is macOS's responsibility, not an isolation boundary between arbitrary helper/child processes.

**Migration:** configurations without `systemAudioApplicationID` disable app audio on decode. Keeping the old enable bit would silently broaden window/exclusion-scoped audio to all apps. Other choices are retained. Once a scope is chosen and enabled, it persists normally. The menu labels the audio scope and warns about default-microphone selection.

#### OBS configuration for this machine

OBS 31.0.1 satisfies the documented OBS 30+ native macOS Audio Capture requirement [O1]. The saved Ableton video source is not the same thing as a persistent dedicated music source.

1. Add **macOS Audio Capture → Application → Ableton Live**, with Live running. Use the same existing audio source in each required scene (or a shared audio scene included in each), rather than separately instantiating captures.
2. Disable/mute the audio contribution from Ableton's Screen Capture source and any overlapping desktop/virtual feed. Do not disable the new dedicated source when switching to a camera scene. OBS 28/29's older screen-capture method removes audio when hidden; “hide the screen source” is not a portable audio-only recipe [O1].
3. Keep **Settings → Audio → 48 kHz → Stereo** for this route. Choose a specific working microphone; the saved headphone-input UID needs verification before relying on it. Do not also add that same mic as a duplicate scene source.
4. In **Advanced Audio Properties**, keep music **Monitor Off** when already listening through Live. “Monitor Only (mute output)” does not send that source to the audience; “Monitor and Output” can double it if the monitor device is captured.
5. Assign the complete audience mix to the streaming track; assign optional isolated music/mic tracks to recording. Verify the chosen player/editor exposes multiple tracks. Configure VOD track separately if desired; recording stems alone do not alter the live mix.
6. Measure camera/voice/music sync using the file, not a delayed browser stream. Use per-source sync offsets only after stable routing is established. Record every scene transition, then listen back.
7. Use **one** fallback virtual route only if native capture fails the actual Live bus/channel requirement. BlackHole 2ch + a deliberate Multi-Output device is free; Loopback provides explicit app/channel/monitor routing [O2]. Avoid feeding both native and virtual copies into the mix. Do not alter system default output just to capture audio when native app capture already works.

#### Required hardware qualification before treating a setup as show-ready

- AirPods output with mic disabled; AirPods output with explicit Mac/USB mic; open the actual chat/browser/dictation apps. Check playback quality, recording and perceived playing latency. Repeat reconnect/automatic-switch recovery in a private session.
- Speakers with mic disabled, then intentional voice at safe speaker volume. Confirm no acoustic doubling or loop.
- Real Live set: main/cue/metronome/sample preview, left/right, plug-in helpers, external instruments, intended interface inputs. Native app isolation must also be checked against an unrelated app producing sound.
- Real camera clap/transient at beginning and end of the intended stream duration; sustained CPU load with webcam/chat; test device removal, app quit/relaunch, display removal and sleep only in a private recording.
- Verify recorded music and mic, stream-track assignments, disk capacity and provider delivery separately. Software fixture tests do not replace this matrix. No AirPods/interface model, actual Live playback session, or real OBS broadcast was qualified in this change.
